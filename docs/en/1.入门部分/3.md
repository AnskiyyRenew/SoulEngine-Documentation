## How to ask questions correctly

### Preparation before asking

- Search for existing answers first: this documentation, FAQ, GitHub issues, Stack Overflow, or search engines, and confirm that the issue is not already known or duplicated.
- Try to simplify the problem: identify the smallest affected scope (module, file, configuration), and see whether it can be reproduced locally.

### How to describe the problem (required information)

- Environment information: operating system, language/runtime version, dependencies or framework versions.
- Expected behavior vs actual behavior: clearly explain what you expect and what is actually happening.
- Error information: full error stack or logs (do not only copy one line), and indicate when or how the error occurs.
- Reproduction steps: list the minimal steps that reliably reproduce the problem, ideally everyone can follow them.

### Provide a minimal reproducible example

- Provide a runnable minimal code snippet or a minimal repository link (remove unrelated content).
- Avoid sharing sensitive information (API keys, passwords, private data); if necessary, use placeholders.
- Explain how to run the example: commands, input, expected output.

### Solutions you have already tried

- List the steps you already attempted and their results (including documentation or links you checked).
- Explain what suspicious points you found and what you think the root cause might be.

### Question etiquette (improves the chance of getting help)

- Use a concise, descriptive title that includes relevant error keywords or context.
- Structure the content clearly, write concisely, and use code blocks for code and logs.
- Be courteous and explain what kind of help you are looking for (solution idea, code fix, debugging guidance, etc.).
- Share the solution promptly once found and close/update the issue.

Following these points can significantly increase the chance of receiving effective help.

## Code style guidelines

### Naming conventions

- Use `snake_case` for variables and functions.
- Use `UPPER_SNAKE_CASE` for constants.
- Use `PascalCase` for classes/modules.
- Avoid single-letter variable names unless they are used in a short loop like `i`, `j`, or `k`.

### Code formatting

- Use 2 or 4 spaces for indentation (keep the project consistent).
- Do not make lines of code too long.
- Add blank lines between logic blocks to improve readability.
- Use `local` to declare local variables and avoid polluting the global scope.

### Comments and documentation

- Add comments for complex logic and public functions.
- Use Lua documentation comments starting with `---` to describe function parameters and return values.
- Keep comments concise and avoid over-commenting.

### Function design

- Keep each function focused on a single responsibility.
- Functions should have a clear return value contract.

### Error handling

- Provide meaningful error messages to make debugging easier.
